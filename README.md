# futsal-calendar

Sync a Catalan Futsal Federation (FCF) team's matches to a subscribed calendar (`webcal://`, RFC 5545) in Apple Calendar or any other compatible client. When the FCF changes a match's date, time, venue, or status, the calendar updates itself — no download or re-import required.

Node/TypeScript backend on Vercel serverless functions + Angular 17 frontend to pick a team and get the subscription URL.

**Status: working end to end.** Deployed at `partitsalcalendari.com`, with a real subscription verified on an iPhone. 257 tests, `tsc --strict` with no `any`.

## How it works

1. The user picks discipline → competition → group → team in the wizard at `/`.
2. That leads to `/equip/{groupId}/{teamId}`, with the team's calendar and a subscribe button whose behavior depends on the device (see "Platform-aware subscription" under Design decisions): on Apple it opens `webcal://.../api/calendar/{groupId}/{teamId}.ics` directly; on any other device it copies the `https://` URL and guides the user to add it from their calendar app.
3. The calendar client (Apple Calendar, Google Calendar...) subscribes to that URL. Every time it re-fetches it, it gets a `.ics` generated on the spot from the FCF's current data — no cache or database in between.
4. Each event's `UID` is stable (`fcf-{CODACTA}@partitsalcalendari.com`), so a date/time/venue change updates the existing event instead of creating a duplicate.

There's no way to force a calendar client to refresh instantly — the app never promises instant sync, only automatic sync.

## Architecture

```
domain/                  Match, TeamRef, Venue, MatchStatus, catalog — knows nothing about the FCF
federation/fcf/*          the only place that knows about fcf.cat: providers, date parsing, mappers
matches/                  filtering by team (never by name — two clubs can share a name)
calendar/                 ICS generation (RFC 5545) + orchestration + content ETag
http/                     framework-agnostic HTTP handlers (request/response as plain objects)
api/                      thin Vercel adapters — delegate everything to http/
scripts/dev-server.ts     local node:http adapter, same handler as Vercel
web/                      Angular 17 frontend (selection wizard + team calendar)
```

General principle: the FCF stays completely isolated behind `FederationProvider`/`CompetitionCatalogProvider` (port) and its `Fcf*` implementations (adapter). The rest of the app only knows its own domain model.

## Running locally

The backend and frontend are two separate processes (the frontend calls `/api/*` over HTTP).

```bash
# Terminal 1 — backend, port 3000
npm install
npm run dev

# Terminal 2 — frontend, port 4200 (proxies /api to 3000)
cd web
npm install
npm start
```

Open `http://localhost:4200/`. The proxy (`web/proxy.conf.json`, referenced from `angular.json`) is only needed locally — on Vercel, the frontend and the `api/` functions live under the same domain, so `/api/*` works without a proxy.

To test just the backend:

```bash
curl -i http://localhost:3000/api/calendar/{groupId}/{teamId}.ics
curl -i http://localhost:3000/api/disciplines
```

## Environment variables

None is required — the app works with its defaults. Set them in Vercel (Project Settings → Environment Variables) if you need to adjust them without a new code deploy:

| Variable | Effect | Default |
|---|---|---|
| `FCF_USER_AGENT_CONTACT` | Adds a contact (email) to the `User-Agent` header the app sends to the FCF on every request. | none |
| `FCF_DEFAULT_TEMPORADA_ID` | `temporada` id used by `/api/competitions` when the client doesn't specify one. The FCF doesn't expose a stable "current season", so this value needs a yearly check when the FCF opens the next season (confirm against `/api/competition/temporadas` before changing it). | `22` |

`DEFAULT_UID_DOMAIN` (the domain used in each ICS event's `UID`) is **deliberately not** configurable via environment: changing it would generate different UIDs for existing matches, which Apple Calendar (and any RFC 5545 client) would interpret as new duplicate events instead of updates. It's fixed in code (`src/calendar/ics-config.ts`) to the real deployment domain.

## Deployment (Vercel)

`vercel.json`:

```json
{
  "buildCommand": "cd web && npm install && npm run build",
  "outputDirectory": "web/dist/web/browser",
  "rewrites": [{ "source": "/((?!api/).*)", "destination": "/index.html" }]
}
```

`outputDirectory` points at `browser/` because Angular 17's `application` builder always writes there, even without SSR. The rewrite is a standard SPA fallback: Vercel first serves any static file or `api/` function that exists, and only falls back to `index.html` when nothing matches.

The backend script that runs `tsc --noEmit` is called `typecheck`, not `build` — Vercel automatically runs `npm run build` if that script exists (even without configuring it in the dashboard), and with `NODE_ENV=production` it doesn't install `devDependencies`, so `tsc` wouldn't even be available. The `api/` functions are compiled on the fly from `.ts` by Vercel's own Node runtime.

## Monitoring

`GET /api/health` is a deep health check, not just "is the server up": it calls the FCF for real (`listDisciplines()` and `getMatches()` for a known real `grupId`, concurrently) and only returns `200 {"status":"ok",...}` if both actually succeed. If either fails — the FCF blocks us, changes its response shape again, times out, anything — it returns `503 {"status":"down","checks":{...}}` with each failing check's error message (truncated), so the response itself is enough to diagnose what broke without needing to check Vercel's logs first. Each FCF call uses a short 5s timeout and no retries (`maxRetries: 0`), deliberately different from the 8s/2-retries the rest of the app uses: a health check that takes 24s+ to fail is worse than a Vercel function timeout, and a transient blip shouldn't need a retry here — the monitor will just ask again on its own next cycle. `Cache-Control: no-store`, since caching a health check defeats the point.

This exists so a future FCF-side break (there have already been three: a date-format change, a `Referer`-based block, and a `partidos` response reshape — see "Design decisions" below) gets noticed without anyone having to remember to check the site. The endpoint itself doesn't alert anyone — set up a free external uptime monitor (e.g. [UptimeRobot](https://uptimerobot.com) or [Better Uptime](https://betteruptime.com)) to `GET https://partitsalcalendari.com/api/health` every 5 minutes and notify on anything other than `200`. That's a one-time, no-code setup on the monitor's side; deliberately not a Vercel Cron Job calling a webhook, which would mean writing and maintaining notification code (Slack/Discord/email) in this repo for something a free third-party service already does well — not worth it for a hobby project's single health endpoint.

## Design decisions

**Time zone**: the FCF returns dates like `"2026-09-26 18:30:00"`, Europe/Madrid local time, with no offset. They're never parsed with `new Date(string)` (ambiguous/runtime-dependent); `shared/timezone.ts` uses `Intl.DateTimeFormat` to resolve the real offset (CET/CEST) at that specific instant and explicitly convert between wall time and UTC.

**Stable UID**: `fcf-{CODACTA}@partitsalcalendari.com`. `CODACTA` is the FCF's own match identifier and doesn't change even if date/time/venue/status change — that's what lets an update be a real update instead of a duplicate event.

**No external ICS library**: the subset of RFC 5545 in use is small and stable, and the two delicate parts (UTF-8 octet-level folding, `TEXT` escaping) are isolated in `ics-text.ts` with edge-case tests. Switching to a library like `ical-generator` is a mechanical change if it's ever needed.

**`SEQUENCE` fixed at `0`, `DTSTAMP`/`LAST-MODIFIED` always "now"**: computing a real `SEQUENCE` would require persisting the last known snapshot of each match in order to diff it. Without that persistence, any other value would be made up. The practical impact is low: `SEQUENCE` matters mostly in iTIP invitation flows (organizer/attendees); this is a read-only **subscribed** calendar (`METHOD:PUBLISH`), and calendar clients replace the event by `UID` on every refresh, without diffing against `SEQUENCE` — behavior already confirmed with a real subscription on an iPhone.

**Content ETag, not ICS-text ETag**: since `DTSTAMP`/`LAST-MODIFIED` change on every generation, an ETag over the full ICS text would always change, defeating the cache. `match-content-hash.ts` computes a SHA-256 only over the fields a subscriber actually cares about (teams, schedule, venue, status, calendar name) — stable as long as that data doesn't change, enabling a real `304`.

**30–60 minute Cache-Control, no promise of instant sync**: caps how long an HTTP-compliant client reuses the response, but doesn't control when Apple Calendar (or another `webcal://` client) re-fetches the URL — that's up to the client, not the server.

**No cron or persistence (for now)**: live generation on every request (with `Cache-Control` + ETag) already handles immediate change propagation and cache reuse by HTTP-compliant clients. The only thing it doesn't give us is a real `SEQUENCE`/`LAST-MODIFIED` (see above). Introducing cron + persistence would make sense if real signals show up: FCF outages observed in production, more subscribers than a live request can sustain, or a genuine need for a correct `SEQUENCE` (for example, if the project moved to an invitation-based flow). If it's ever needed, the only thing worth persisting is "the last known match snapshot per group" — a simple key-value store (e.g. Vercel KV) is enough, not a relational database.

**Always filter by team id, never by name**: two different clubs in the same group can share text in their name (seen in real data), so all filtering uses `CODEQUIPO_CASA`/`CODEQUIPO_FUERA`.

**FCF statuses**: only what's confirmed against real data is mapped (`scheduled`); any other code is an explicit `'unknown'` instead of a guessed translation.

**Cascading selector instead of free search**: the FCF's club-name search (`/api/clubs/search`) is broken for Futsal (returns no teams), confirmed against the real API. The wizard instead uses the FCF's own cascading catalog (discipline → competition → group → team), verified end-to-end and with the same schema across every discipline.

**Framework-agnostic HTTP handlers**: `handle*Request()` takes and returns plain objects (`{method, url, ...}` → `{status, headers, body}`), with no Vercel or `node:http` types. The `api/` and `scripts/dev-server.ts` adapters are each a ~20-line translation to their concrete runtime, which lets the handlers be tested without mocking either one.

**Platform-aware subscription**: the Google Calendar app for Android has no way to subscribe to a URL directly (confirmed — it's a known limitation of the app itself, not something a client can work around), so a single `webcal://` link button only really works on Apple. `AddToCalendarButtonComponent` detects the platform from `navigator.userAgent`: on Apple (iOS/macOS) it keeps the one-tap `webcal://` link; on any other device, the primary button becomes "copy URL", together with a shortcut to Google Calendar's add-by-URL screen and instructions for that flow.

**Score in `SUMMARY`, independent of status**: once the FCF publishes numeric `GOLES_CASA`/`GOLES_FUERA` for both sides, `mapFcfMatch` attaches a `score` to the `Match` and the event's `SUMMARY` becomes `⚽ FINAL · Home X - Y Away`. This is deliberately **not** gated on `status === 'finished'`, even though that status code (`CERRADA=1, ESTADO=1`) is now confirmed: score presence is a direct, observable signal on its own, and stays correct even for any future status combination we haven't seen yet. `match-content-hash.ts` includes the score so a result landing (or being corrected) busts the ETag like any other change.

**Team crests**: `ESCUDO_CASA`/`ESCUDO_FUERA` are bare filenames, not URLs (the original assumption that they were ready-to-use links was wrong — never actually verified against real data). Confirmed 2026-09 by inspecting real `<img>` requests on fcf.cat's own competition pages: every crest resolves at `https://files.fcf.cat/escudos/clubes/escudos/{filename}`. `mapTeam` in `fcf.mapper.ts` builds that full URL; the UI renders it next to the team name and hides the `<img>` on load error (no initials fallback) rather than showing a broken image.

**Visual design**: the UI's look and feel (colors, typography, spacing, layout) was designed with [Google Stitch](https://stitch.withgoogle.com/), Google's AI-assisted UI design tool, starting from this project: https://stitch.withgoogle.com/projects/6523744783108261217. The resulting design tokens were ported by hand into plain CSS custom properties in `web/src/styles/_tokens.scss` — no runtime dependency on Stitch.

The header logo (`AppShellComponent`) uses the full lockup from the Stitch "catfutbol_senyera_logo" export — the senyera-striped badge with the ball, plus the "CATFUTBOL" wordmark baked into the same SVG — inlined in the template (it's a dozen small paths, not worth a separate asset file or an extra HTTP request) and recolored to the exact token hex values (`#D91424`/`#FFC700`/`#121C3B`) instead of the mockup's slightly-off `#FFD100`/`#0F2042`, so the logo and the rest of the UI are drawn from the same palette. **2-column grid for competition/group/team steps, desktop only, not discipline**: `SelectorStepListComponent` (`web/src/app/shared/selector-step-list/`) takes a `layout: 'list' | 'grid'` input, defaulting to `'list'`. `team-selector.page.html` passes `layout="grid"` for the competition, group and team steps — the ones that can list dozens of items — but leaves the discipline step (always ~7 items) on the default single column, exactly as asked. The grid is mobile-first single-column and only becomes 2 columns from a 768px viewport upward: a first pass tried 2 columns everywhere with a narrow-phone fallback, but on a real phone even the "wide enough" widths still cut most names down to 2-3 words, which read worse than the plain list it replaced — this app's primary audience is a phone subscribing to a calendar, so mobile keeps the original single column and only desktop/tablet gets the grid's shorter-scroll trade-off. The page container itself (`.team-selector`) was capped at `max-width: 640px` regardless of viewport — fine for a single column, but it meant the grid's two columns would still only be ~300px wide on desktop, clipping most competition names hard. A `team-selector--wide` modifier (bound to the same "not discipline" condition, same 768px breakpoint) widens that cap to 960px on desktop/tablet only; mobile stays at 640px, single column, unchanged from before the grid was introduced.

**Senyera stripe on every selector card, matching the next-match hero's accent**: each card in `SelectorStepListComponent` (discipline, competition, group and team alike) keeps the card's own `border-radius: var(--radius-lg)` rounded on all four corners, and gets a 4px senyera-striped left edge — 9 equal **horizontal** bands (5 gold `var(--color-tertiary)`, 4 red `var(--color-primary)`, starting and ending gold) via a hard-edged `linear-gradient(to bottom, ...)` on a `::before`, flush with the card (`top/left/bottom: 0`, `width: 4px`) and given its own matching `border-radius: var(--radius-lg) 0 0 var(--radius-lg)` so it sits inside the card's rounded left corners instead of being cut by them. The width and position deliberately match `next-match-hero.component.scss`'s own `border-left: 4px solid var(--color-primary)` accent — same treatment, just striped instead of solid. This went through several earlier layouts (full-width top strip in both orientations, a wider 10px left strip, a version extended 1px past the card's own box to close a seam, and a brief experiment squaring off the card's left corners entirely to sidestep the rounding question) before settling back here, on explicit request. **Known limitation, inherent to the technique**: a solid single-color `border-left` (as in `next-match-hero`) gets a smooth native taper around a rounded corner, because the browser blends differing border-side widths through the curve — a `::before` overlay with its own independent `border-radius` can only be clipped into its own rounded rectangle, so the corner reads as a clean rounded inset rather than a true taper. Verified in a local Playwright render (4x DPI, cropped to the card) that it reads as rounded, not cut — just not pixel-identical to the hero's native corner.

**Every upcoming match gets the same hero-style card, no separate "next match" section**: `TeamCalendarPage` used to render the single next match with `NextMatchHeroComponent` (a larger, distinct card) and every match after it with the plain, borderless `MatchListItemComponent`, in two separate sections ("Pròxim partit" / "Pròxims partits"). This is now one "Pròxims partits" section that renders every entry in `upcomingMatches()` with `NextMatchHeroComponent` — so instead of one highlighted card followed by a plain list, all upcoming matches look like equally-weighted cards (border, `border-left` accent, shadow, rounded corners), stacked with `--space-md` gaps via the new `team-calendar__list--cards` modifier. `MatchListItemComponent` stays as-is for "Partits jugats" (past results weren't part of this request) — the two components now diverge in role: `NextMatchHeroComponent` for anything upcoming, `MatchListItemComponent` for history. The `nextMatch` computed signal stays for the `SportsEvent` JSON-LD (a separate SEO concern); the `laterMatches` computed was removed as dead code once the template stopped needing the split.

**CASA/FORA badge instead of "Programat" on upcoming match cards**: `NextMatchHeroComponent` used to always show `app-status-badge` next to the round number, which for any upcoming match just says "Programat" — true but not useful once every card shows a scheduled match. It now shows that generic status badge only when the status is genuinely informative (`postponed`, `cancelled`, `finished`, `unknown`); for `scheduled` matches it instead shows whether the viewed team is playing at home or away, reusing `isHome()` (already computed for team-name bolding). Colors reuse existing brand tokens rather than adding new ones: `CASA` is `var(--color-tertiary)`/`var(--color-on-tertiary)` (the brand gold), `FORA` is `var(--color-secondary-container)`/`var(--color-secondary)` (the existing light-blue/navy pair already used elsewhere) — no new tokens needed.

**Logo centered in the header on mobile, left-aligned on desktop**: `app-shell.component.scss`'s `&__header` is `display:flex` with just the brand link inside; it defaults to `justify-content: center` (mobile-first, matching the same 768px breakpoint used for the selector grid and the wide team-selector container) and switches to `justify-content: flex-start` at `@media (min-width: 768px)`.

**Crest on the team page, group/discipline/competition breadcrumb deliberately removed**: an earlier version also showed a "discipline · competition · group" line under the team name, fetched from a dedicated reverse-lookup endpoint (`GET /api/groups/{grupId}/context`, built by walking the catalog tree). That lookup only ever resolved for the disciplines actually crawled (futsal), so it silently failed to render for most non-futsal teams — confusing, so it was removed outright. The crest above the name reuses `TeamRef.crest`, already present on any match, and needed no lookup of its own — it stays. `src/catalog/group-context.ts`, the walk this endpoint was built on, was removed too once its only other caller (the team search index, below) was also removed — it has no remaining use anywhere in the app.

**Played matches are cards too, deliberately plainer than the upcoming-match cards**: `MatchListItemComponent` was a borderless row separated by `border-bottom` (a classic list). It's now a card — `background`, `border`, `border-radius: var(--radius-lg)` — so "Partits jugats" reads consistently with "Pròxims partits" (both cards, stacked with the same `team-calendar__list--cards` gap modifier) rather than one section of cards and one section of plain rows. The two card styles are deliberately NOT identical: `NextMatchHeroComponent` keeps `--color-surface` (white), the `border-left` accent, `box-shadow` and an internal divider under the meta row; the past-match card uses `--color-surface-container-low` (a light lavender tint already in the palette) with no accent border, no shadow, no internal divider — flatter and quieter, since these matches are settled history, not something to act on. No new tokens needed.

**One route per wizard step, not one route with the whole chain in query params**: `TeamSelectorPage` used to live entirely at `/`, pushing `?disciplinaId=&competicioId=&grupId=` onto the same route as the user stepped forward (`router.navigate([], { queryParamsHandling: 'merge' })`). That does push a browser history entry, but since Angular reuses the same component instance across query-param-only navigations on an unchanged route, and the component only read `route.snapshot.queryParamMap` once, in the constructor, pressing the browser's back/forward button changed the address bar without ever touching the component's signals — the page just sat there frozen. Fixed by giving each step its own route instead: `/`, `/competicio/:disciplinaId`, `/grup/:disciplinaId/:competicioId`, `/equips/:disciplinaId/:competicioId/:grupId` (all four resolve to the same `TeamSelectorPage`, Angular's normal pattern for a parameterized page). Distinct routes get recreated by the router on every navigation — including back/forward — so `disciplinaId`/`competicioId`/`grupId` are read fresh via `toSignal(route.paramMap)` every time, and a single `effect()` fetches only the one list the current step actually renders (previously all three catalog calls could accumulate in memory across a forward walk; now each step's component instance fetches just its own list, relying on the catalog endpoints' existing hour-long `Cache-Control` for anything repeated). `/equips/...` (plural) for the team-selection step, not `/equip/...` (singular) — that's the existing team-calendar route (`/equip/:groupId/:teamId`), a different page with a different param shape.

**SEO — dynamic `Title`/`Meta`/canonical/JSON-LD, no static route titles**: `SeoService` (`web/src/app/core/services/seo.service.ts`) updates `<title>`, description, Open Graph/Twitter tags, the canonical `<link>`, and a `SportsEvent` JSON-LD block from each page's own component, once real data (team name, next match) is available. Angular Router's static `title:` route property was tried first and removed: it fired on every route identically and overwrote the good default title from `index.html` with a generic one, for every team page alike — actively worse than doing nothing.

**SEO for bots — dynamic rendering via a Vercel header-matched rewrite, not full SSR**: the Angular app is CSR-only (no Angular Universal), so anything `SeoService` sets is invisible to bots that don't execute JS (link-preview scrapers for WhatsApp, X, LinkedIn, Slack, iMessage — Googlebot itself does execute JS and doesn't need this). Rather than migrating to Angular SSR, `vercel.json` rewrites `/equip/:groupId/:teamId` to `api/team-page.ts` **only** when the request's `user-agent` header matches a known bot pattern (Vercel's `has` rewrite condition); everyone else still gets the normal SPA. `team-page-http-handler.ts` renders a small, real HTML page (title, description, canonical, OG/Twitter tags, the same `SportsEvent` JSON-LD, an `<h1>`, and the team's upcoming matches) from the same `FederationProvider`/`CompetitionCatalogProvider` the rest of the backend already uses. This is Google's documented "dynamic rendering" pattern, not cloaking, because the bot-served content matches what a user would see once the SPA finishes loading — it's a much smaller change than an SSR migration and can be replaced by one later without touching the rest of the app.

**Sitemap scoped to 2 of 7 FCF disciplines, crawled and cached, not persisted**: `sitemap-crawler.ts` walks the FCF's own discipline → competition → group → team catalog to list every team page. Measured live against production before building it: all 7 disciplines together are ~460+ groups just for temporada 22's futsal disciplines alone, and other disciplines (Futbol 11, Futbol 7, Futbol 5, Futbol Platja) push that much higher. `SITEMAP_DISCIPLINA_IDS` deliberately limits the crawl to Futbol Sala and Futbol Sala Femení — the disciplines this app is actually built for — with bounded concurrency (`pMapLimit`, 6 at a time) and best-effort skip-on-error per branch (one bad competition or group is logged and skipped, matching `FcfFederationProvider`'s existing philosophy of not letting one bad branch abort the whole request), **except** when every configured discipline fails at the top level (e.g. the FCF is fully down): that specific case throws instead of silently returning an empty page list, precisely so the cache below sees it as a failed crawl and keeps serving the last known-good sitemap instead of overwriting it with an empty one. The result is cached in memory for 12h (`sitemap-http-handler.ts`), with the last successful crawl kept and served if a later crawl fails, and a bare homepage-only fallback if there's never been a successful crawl at all. Trade-off accepted deliberately: a Vercel cold start resets this cache (no persistence, matching the project's "no DB for now" stance elsewhere), so the first request after a cold start pays the full crawl cost — mitigated by the generous `maxDuration: 60` on that function and the 6h HTTP `Cache-Control` telling well-behaved crawlers not to hit it too often either.

**Team search autocomplete — built, removed over a rate-limit scare, briefly restored, removed again for good after a real crash**: a home-page autocomplete would have let someone who knows their team's name skip the discipline → competició → grup → equip wizard (`src/catalog/team-search-index.ts` built a flat index for one discipline at a time via a discipline → competition → group walk plus `catalog.listTeams(groupId)` for every group found that way; `GET /api/teams/search?disciplinaId=&q=` served it, cached per discipline with a last-known-good fallback, the same pattern `sitemap-http-handler.ts` uses; `TeamSearchComponent` rendered it on `TeamSelectorPage` once a discipline was chosen). It came back, architecturally unchanged (scoped to one discipline at a time, never "every discipline"), once it turned out the block that followed that first removal was actually unrelated (see the next entry) — so the original rate-limit concern, while real, wasn't the full story. Restoring it surfaced a second, independent, and more immediate problem: running a second search in the same session crashed the app. That crash was not root-caused — rather than debug a convenience feature that had now caused two separate real problems, it was removed again, this time for good: no index, no endpoint, no autocomplete UI, same as the first removal. The lesson that stays: anything that walks the FCF's catalog in bulk (the sitemap crawler, the old breadcrumb lookup below) is still a request-volume risk worth the same scrutiny; team search specifically is not coming back a third time without a much more careful look at both the crawl-volume risk and whatever caused the crash.

**The apparent FCF block was actually an FCF date-format change, caught by comparing raw FCF JSON against this app's own output**: right after removing team search, the calendar/matches and team-selector pages also appeared to stop working for every team — looking, at first, like the same FCF block had spread to the rest of the app. Direct checks against the running dev server (`/api/disciplines`, `/api/groups/{grupId}/teams`, `/api/matches/{groupId}/{teamId}`) all came back `200` with real data, so nothing was actually blocked. Fetching the FCF's own raw JSON for a real `grupId` and comparing it side by side with this app's response for the same group found the real cause: the FCF had changed `COMIENZO1` from `"2026-09-26 18:30:00"` (space-separated) to `"2026-09-26T18:30:00"` ("T"-separated, still no timezone suffix) for the new season. `parseFcfDate` only accepted the space form, threw on every match, and `mapFcfMatch` caught that per-match and silently skipped it — every team's calendar looked genuinely empty, with no error visible anywhere in the UI, and crests disappeared too (`enrichTeamsWithCrests` in `catalog-http-handler.ts` derives them from match data, so a matches failure silently took crests down with it). `FCF_DATE_PATTERN` in `fcf-date.ts` now accepts `[ T]` as the date/time separator, while still rejecting a trailing timezone marker (`Z`, `+02:00`): accepting "T" as a separator is not the same as accepting ISO 8601 wholesale — a real UTC instant means something different from the naive Europe/Madrid wall-clock time this function assumes, so that case still throws, with tests guarding it. This also means the FCF was never actually blocking this app during that incident — the block team search was blamed for didn't exist; team search's real problems turned out to be different (see the previous entry).

The underlying "no matches yet" state itself is unchanged and correct — `upcomingMatches`/`pastMatches` are genuinely empty, and "No hi ha cap partit programat de moment." is the right thing to show — this only fixes the page not knowing the team's own name and crest while that's true.

**Postponed matches (`AJORNAT`) are now a real status, not `unknown`**: confirmed live against grup 60090763 — two matches the FCF's own site flags with a red `AJORNAT` badge both carry `CERRADA="0", ESTADO="2"`, distinct from a normal scheduled match's `CERRADA="0", ESTADO="0"`. `mapFcfStatus` now maps that combination to `'postponed'` instead of falling through to `'unknown'`. The rest of the pipeline already supported this status end to end and needed no further change: `match-content-hash.ts` already hashes `status`, so the ETag already busts correctly when a match flips to postponed; `mapMatchStatusToIcsStatus` already maps `'postponed'` to `STATUS:TENTATIVE`; the frontend's `StatusBadgeComponent` already had an "Ajornat" label and its own `--postponed` CSS class, only ever unreachable because the backend never produced the status. `generateIcs`'s `SUMMARY` didn't say anything about postponement either, so a subscriber would see an ordinary-looking fixture; `buildSummaryText` now prefixes a postponed match's title with `📅 AJORNAT ·` (skipped if the match already has a score, which wins and shows `FINAL` instead — a scored match is settled, not postponed). `DTSTART`/`DTEND` are left exactly as the FCF reports them: the FCF keeps `COMIENZO1` at the original kickoff while a match is flagged postponed (confirmed on both real examples) and only moves it once a new date is actually set, so the calendar entry stays on its original day with the new title until that happens — the stable `UID` already means that eventual date change updates the same event rather than creating a new one, with no further code needed. The badge color (`--color-status-postponed-bg`/`-text`) is amber — see the next entry for why, and why that's a deliberate departure from the FCF's own red for this status.

**Suspended matches (`SUSPÈS`) get their own status, visually distinct from `AJORNAT`**: also found live in grup 60090763, on the same matchday as the postponed example above — three matches the FCF flags with a red `SUSPÈS` badge all carry `CERRADA="0", ESTADO="3"`, a third code distinct from both `scheduled` (`0|0`) and `postponed` (`0|2`). `MatchStatus` (domain and frontend) gained a `'suspended'` member, `mapFcfStatus` maps `0|3` to it, and `mapMatchStatusToIcsStatus` maps it to `STATUS:TENTATIVE` for the same reason as `postponed` — a suspended match isn't confirmed to not happen, it's expected to get a new date like a postponed one, so `CANCELLED` would overstate it. The FCF's own site renders `SUSPÈS` in the same red as `AJORNAT`, but this app deliberately doesn't: they're different situations and the user asked for them to read as different at a glance. The first pass gave `postponed` red (matching the FCF) and `suspended` amber; on review that was backwards for what each status actually means here — `postponed` (`AJORNAT`) already has the delay acknowledged and, in practice, settles into a new date soon, while `suspended` (`SUSPÈS`) is the more disruptive, open-ended one (stopped outright, no new date yet) — so the two color pairs were swapped: `--color-status-suspended-bg`/`-text` is now the red FCF uses for both, `--color-status-postponed-bg`/`-text` is amber, and `cancelled` keeps its own separate red so a swipe through the three still reads as three different things. `generateIcs`'s `buildSummaryText` prefixes a suspended match's title with `❌ SUSPÈS ·` (first tried `⚠`, swapped for `❌` on request — a plain cross reads as "this one's off" faster than a warning triangle does), and postponed's with `📅 AJORNAT ·` — deliberately different pictograms (calendar for "will get a new date" vs. cross for "stopped") rather than reusing `postponed`'s original `⏸`, so the two read apart in a calendar app's list view too, not just on the badge (same score-wins rule as before: a scored match shows `FINAL` regardless of status). Every other part of the pipeline — the ETag hash, the generic status-badge fallback already used by `NextMatchHeroComponent`/`MatchListItemComponent` — needed no change, same as when `postponed` was added.

**`StatusBadgeComponent` now matches the typography of `NextMatchHeroComponent`'s own CASA/FORA pill, not just its box shape**: both already shared `display: inline-flex`, the same padding, radius, and 12px font-size, but `status-badge` used a lighter 500 weight with no letter-spacing and the label text as written ("Ajornat", "Suspès", "Per confirmar"), while the home/away pill was 700-weight, letter-spaced, and literally uppercase ("CASA"/"FORA") — next to each other in the "Pròxims partits" list, the status badge read visibly smaller and sat slightly off from the home/away pill despite having identical box metrics. `status-badge.component.scss` now also sets `font-weight: 700`, `letter-spacing: 0.03em`, and `text-transform: uppercase`, so every status label (not just `postponed`/`suspended`) renders the same way the home/away pill always has.

**Production went down: the FCF started returning `403` for every `/api/competition/*` call, traced to a missing `Referer` header, not an IP block**: Vercel logs showed every live request — `/api/disciplines`, `/api/calendar/{groupId}/{teamId}` — failing with `FCF endpoint returned HTTP 403`, body a CloudFront error page ("Request blocked... too much traffic or a configuration error"), and the production site itself showing "No s'ha pogut carregar la llista de disciplines." Reproduced directly: navigating straight to `https://www.fcf.cat/api/competition/disciplines` in a browser (no referring page) returns that same `403`/CloudFront page — confirmed live, this isn't Vercel-specific. But loading the FCF's own competition page and reading its network requests showed the identical endpoints (`disciplines`, `partidos?grupId=...`) returning `200` from JS running on that page, including a bare `fetch(..., { credentials: 'omit' })` with no cookies — so it isn't session/cookie-gated either. The one difference between the two: a request made by in-page JS automatically carries a same-site `Referer`; a fresh, standalone request (a new tab, or a server with no browser context) doesn't. That isolates the FCF's new block to "requests without a `fcf.cat` referer", not to IP, ASN, or User-Agent — our existing `futsal-calendar-sync/0.1` UA had worked for weeks before this started. Both FCF-calling clients (`FcfFederationProvider` for `partidos`, `FcfHttpClient` for `disciplines`/`competicions`/`grupos`/`equipos` — two separate implementations, each with its own retry loop, never unified behind a shared base class) now send `Referer: https://www.fcf.cat/ca/competicio` alongside the existing `Accept`/`User-Agent`. This is a plausible fix based on solid evidence (refererless request → `403`, same-site request → `200`, same network both times) but it hasn't been confirmed against production yet — that needs a real deploy and a check of the Vercel logs/the live site after. If it turns out the FCF's WAF is actually keying on browser-only `Sec-Fetch-*` metadata instead (which a server-side `fetch` can still set explicitly, just wasn't tried here first since `Referer` is the far more common and far simpler CloudFront/WAF rule), that's the next thing to try.

**Update on the above — the `Referer` fix worked, but `partidos` is still down, now for a different reason**: after deploying it, production logs confirm `/api/disciplines` and `/api/groups/{grupId}/teams` both now return `200` — the `403` is gone for those. `/api/matches/{groupId}/{teamId}` (and therefore `/api/calendar/{groupId}/{teamId}.ics`) is still broken, but the error changed: no longer `FCF endpoint returned HTTP 403`, now `FCF endpoint returned an unexpected shape for groupId="..." (expected an object mapping jornada -> match[])`. That means the request is no longer being hard-blocked — FCF answers `200` — but the JSON body isn't the usual `{"1": [...], "2": [...]}` shape our code expects, and reproduced live against the FCF's own site, a same-site in-page `fetch` to the same `partidos` endpoint still returns real match data at `200`, so the FCF itself hasn't changed its normal response shape — whatever our server is now getting back is something else, most likely a soft-throttle response (a small JSON object like `{"message": "..."}`) distinct from the earlier hard `403`, since `partidos` is the heaviest of these endpoints and the one this investigation (plus a day of repeated manual testing against the same `grupId`s) has hit hardest. Confirmed it isn't `grupId`-specific: `58162580` fails the same way `60090763` does. The old error path only logged a generic "unexpected shape" with no detail, which made this genuinely unknown rather than diagnosable, so both `FcfFederationProvider.parseJson` and `FcfCompetitionCatalogProvider.fetchOptions` now append a snippet of the actual malformed body (`JSON.stringify(body).slice(0, 200)`) to the thrown error — the exact same `safeReadSnippet`-for-the-non-JSON-shape-case idea the HTTP-status-error path already had. Not deployed/confirmed yet: the next production log for this error will show the real body for the first time, which should turn "guessing between soft-throttle, a changed response format, or something else" into a known fact and an actual fix.

**Resolved — it was neither a block nor a throttle, the FCF nested `partidos` under a new wrapper key**: the body snippet the improved error now logs gave the real answer: `{"partidos": {"1": [...], ...}, "jornada": {"codjornada": "4", "fecha": "2026-10-24T00:00:00.000Z", "total": 22}}`, confirmed live against the FCF's own endpoint — `partidos` used to be the whole top-level response (`{"1": [...], "2": [...]}`), it's now nested one level deeper under a `"partidos"` key, alongside a new sibling `"jornada"` object (current round number, its date, and the season's total round count — not consumed yet, but there if a "current matchday" feature ever wants it). `FcfFederationProvider.parseJson` now has an `extractMatchesRecord` step before validating the shape: it accepts the matches record either at the top level (the old shape) or nested under `body.partidos` (the new one), the same "accept both, don't assume the old shape is gone for good" approach already used for the `COMIENZO1` date-separator change. This is deliberately not a hard cutover to the new shape only — a provider this dependent on an undocumented third-party API should degrade gracefully across a format the FCF might partially roll back, not just across the one it's on today. `disciplines`/`competicions`/`grupos`/`equipos` were never affected by this nesting change; only `partidos` was restructured.

**Cards in the 2-column grid now stretch to the row's full height, instead of each sizing to its own content**: reported live — two cards on the same row (e.g. a long opponent name wrapping to a second line vs. a short one on one line) visibly differed in height, the shorter one leaving dead space below it instead of matching its neighbour. **The UptimeRobot monitor showing "Down · 404" after `/api/health` was deployed was neither a block nor a stale status — it was a `405`, because the handler only accepted `GET` and UptimeRobot's HTTP monitor checks with `HEAD`**: once the endpoint was live, a browser `GET` to `https://partitsalcalendari.com/api/health` consistently returned a clean `200`, yet UptimeRobot kept reporting the monitor down. The first hypothesis — Vercel's Firewall (System Mitigations / DDoS Mitigation) silently blocking UptimeRobot's checker IPs — looked plausible from the symptom alone but turned out to be a dead end once checked against real data: the Firewall's "Denied" count for the whole project (6 requests/day) was far too low to explain a monitor failing every 5 minutes for 3+ hours, those 6 denied requests were single hits from scattered, unrelated IPs (ordinary background internet noise, not a recurring checker), and Vercel's **System Bypass Rules** — the only way to force-allow a source through system-level mitigations — turned out to not even exist on the Hobby plan this project runs on (Pro/Enterprise only), which would have been a dead end regardless. The real answer came from Vercel's own request logs for `/api/health`, filtered live: every UptimeRobot request was method `HEAD`, each returning `405`, with the Firewall column reading **Allowed** — i.e. Vercel let the request straight through to the function, and the function itself rejected it. `handleHealthRequest`'s `ALLOWED_METHODS` only ever listed `GET` (a sensible default when the endpoint was written, before realizing most uptime checkers probe with `HEAD` first to save bandwidth), so a `HEAD` request got the generic 405 path instead of a real answer. Fixed by adding `'HEAD'` to `ALLOWED_METHODS` and running the exact same FCF checks for it as for `GET` — correctness is what a `HEAD` request is supposed to confirm too — only skipping the JSON body in the response (`body: method === 'HEAD' ? '' : JSON.stringify(...)`), per HTTP semantics: a `HEAD` response must carry the same status and headers a `GET` would, just no body. No adapter changes needed (`api/health.ts`'s `res.end(response.body)` already sends nothing for an empty string), consistent with the "framework-agnostic handler, thin runtime adapter" split documented above. The Firewall detour wasn't wasted effort — ruling it out with real traffic data, rather than guessing further or configuring a bypass that wouldn't have existed on this plan anyway, is what led to checking the actual request logs next, where the real cause was sitting in plain sight.

The three how-it-works cards stack on mobile and become a 3-column grid at the same 768px breakpoint every other grid in this app already uses, reusing the stretch-to-row-height fix from two entries above (`height: 100%; box-sizing: border-box`) so uneven text length never leaves one card visibly shorter than its row siblings.

**Discipline list is now a 2-column grid too, like every other selector step**: the discipline step was the one deliberately left on `layout="list"` in the "2-column grid for competition/group/team steps" entry above, on explicit request at the time. Revisited on explicit request again — `TeamSelectorPage` now passes `layout="grid"` for disciplines as well, reusing `SelectorStepListComponent`'s existing grid mode unchanged, and the page's own container width (previously narrower for the discipline step only, via a `team-selector--wide` modifier applied to every step but that one) is now a single unconditional `960px` desktop max-width for all four steps, since there's no longer a single-column step that needs the narrower measure — the modifier class was removed as dead weight rather than kept around unused.

**Footer credits the author, site-wide**: `AppShellComponent` (wraps every page) gained a `&__footer` below `<main>`, plain centered text ("Fet per Gerard Fernández", linking to the person's LinkedIn profile) in the same quiet, muted style as the rest of the app's secondary text — no social icons, no extra links, exactly what was asked for and nothing decorative added on top.

**Hero background is bold diagonal senyera stripes, drawn as an inline SVG pattern, not a CSS gradient**: the first pass used the app's established 9-band senyera accent (5 gold `--color-tertiary` bars, 4 red `--color-primary` bars, starting and ending gold) as a single 36-stop `linear-gradient(100deg, ...)` with hard color stops, scaled to fill the hero box. Two rounds of feedback refined it — thinner navy gaps (from an even 50/50 split down to roughly 15%-navy/85%-bar) — but the hard-stop gradient itself had a real rendering problem: at a non-axis-aligned angle, browsers rasterize a many-stop hard-edge `linear-gradient` per pixel row, and the stripe boundaries came out visibly jagged/stepped ("una serra") instead of straight diagonal lines — a known limitation of CSS gradients with abrupt color stops at an angle, not something fixable by tweaking stop percentages further. Replaced with an inline SVG `<pattern>`: a small un-rotated tile (navy background rect, a gold `rect` and a red `rect` side by side, 56×40 user units) with `patternTransform="rotate(15)"` doing the diagonal tilt, tiled infinitely across a full-size `<rect fill="url(#...)">`. SVG shape rendering doesn't share the gradient rasterization issue — rotated rects render with clean, straight anti-aliased edges — and it incidentally makes the pattern robust to any hero width instead of needing the band math solved for "exactly 9 bands across 0–100%": it just tiles for however many repeats fit. The fill colors reference the same CSS custom properties (`fill="var(--color-secondary)"` etc.) rather than hardcoded hex, which works in all current browsers for SVG presentation attributes and keeps the pattern on the same token source as the rest of the page. The infinite `<pattern>` tile was itself short-lived: it fixed the jagged edges but, tiling indefinitely, showed far more than the senyera motif's intended 4 red + 5 gold bars on a wide viewport — reported immediately as "too many bars." Replaced with exactly 9 explicit `<polygon>` parallelograms (generated the same way, with a small script, not hand-typed) laid out over a `viewBox="0 0 100 100" preserveAspectRatio="none"` SVG, each polygon's top and bottom edges offset by a fixed horizontal `shift` to produce the diagonal lean without any `rotate`/`skew` transform — `preserveAspectRatio="none"` stretches the 100×100 viewBox independently in x and y to exactly fill the hero box, so baking the slant directly into each polygon's coordinates (rather than transforming a square tile) keeps the math simple and still renders crisp, straight edges at any container width, with the navy gaps simply being the unpainted background `<rect>` showing through between bars. A flat `rgba(18, 28, 59, 0.35)` scrim `<div>` sits between the SVG and the text content (both absolutely positioned inside the now-`position: relative` `.team-selector__hero`, with the text wrapped in one `.team-selector__hero-content` at a higher z-index instead of `position: relative` repeated on each text element) so the white headline/subtitle stay legible over the fully-opaque red/gold stripes.

**Step 3's accent recolored from green to the hero's navy, on request**: `team-selector__how-step--3`'s left border and number-circle swapped `--color-pitch-green`/`--color-status-finished-bg`/`-text` for `--color-secondary`/`--color-secondary-container` — the same navy used throughout the hero background and already paired together elsewhere in the app (the "FORA" away-team pill). Steps 1 and 2 are unchanged (red, then gold), so the three cards still read as three distinct colors, now matching the hero's own palette instead of reaching for the unrelated green already used for finished-match badges elsewhere.

**Disciplines are a 2-column grid on mobile too, but only disciplines**: `SelectorStepListComponent`'s grid mode stayed single-column until 768px for every step, on purpose — competition, group and team names are often long enough that two narrow mobile columns would truncate them hard. Discipline names are short ("Futbol Sala", "Futbol 11"...), so a new opt-in `twoColumnsOnMobile` input lets `TeamSelectorPage` request 2 columns from the smallest width for the discipline step specifically (`[twoColumnsOnMobile]="true"`), while competition/group/team keep the original single-column-until-768px behavior unchanged — a boolean modifier on the existing `layout="grid"` mode rather than a new layout value, since it only ever makes sense combined with grid.

**Ball-icon placeholder removed from every selector card, not replaced**: `SelectorStepListComponent`'s icon circle used to fall back to a generic `sports_soccer` Material icon whenever an item had no crest — every discipline card (disciplines never carry a `crest` in the FCF catalog) and any competition/group/team missing one. Removed on request, with no substitute icon: the icon circle now simply isn't rendered at all for a crest-less item (`@if (hasCrest(item))` around the whole `&__icon` span, not just the `<img>` inside it), so those cards show just the name and chevron, same as a card with a real crest minus the leading circle — applies everywhere this shared component is used, i.e. every step of the selector on every page.

**Team rows stack vertically on narrow cards, via a container query — not a viewport breakpoint**: reported live on a real phone-width devtools view — long club names (compound names with a hyphenated sponsor suffix, common in real FCF data) were truncating hard mid-word in both `MatchListItemComponent` and `NextMatchHeroComponent`'s side-by-side `crest + name | score/vs | crest + name` teams row, and in the hero card an away-team crest was visibly clipped at the card's right edge. The math: on a 393px phone, a single-column card's teams row has roughly 300px of content width split across two crests (32px each), the gaps around them, and the score/vs in the middle — leaving only around 70px per team name column, not enough for a 24-character club name even with the existing 2-line clamp. The same narrowness turns out not to be a mobile-only problem: at the 768px breakpoint where these cards switch into the page's 2-column grid, each grid cell lands around 350–430px wide — similarly tight — so a plain `@media (min-width: 768px)` override (this app's one established breakpoint, used everywhere else) would have fixed phones while leaving the exact same truncation on a mid-size tablet or the desktop grid. Fixed with a CSS container query instead: both cards get `container-type: inline-size`, and a `@container (max-width: 480px)` rule switches `&__teams` from a row to a column (score/vs centered between two full-width team rows, each keeping its natural crest-then-name order — the away team's `row-reverse`/right-align, only ever meaningful for the side-by-side layout, is turned off under the container query) whenever the *card itself* renders under 480px, regardless of whether that narrowness comes from the viewport or from a grid column. This is the first container query in the codebase, a deliberate departure from the single-media-query convention documented throughout this file — justified here because the thing that needed measuring was the card's own rendered width, not the viewport's, and a viewport breakpoint genuinely can't express that.

**Competition and group cards are bigger, 2-column on mobile, and competition names wrap to 2 lines instead of truncating**: once the ball-icon fallback was removed (previous entry), competition and group cards — which almost never have a crest — shrank down to a thin single-line row (small padding, name truncated with an ellipsis), reported as looking cramped on a real phone. `&__card` padding went from `--space-sm` to `--space-md`, and `&__name` switched from `white-space: nowrap` + ellipsis to the same `-webkit-line-clamp: 2` technique already used for match-card team names, with an explicit 15px/1.3 size — competition names in particular are long and easy to confuse with a similarly-worded neighbor ("FASE FINAL COPA CATALUNYA..." vs. "LLIGA DIVISIÓ HONOR CATALANA..."), so letting the full name wrap onto a second line instead of cutting it off was the explicit point, not just a size bump. Applied to `&__name` globally (every step using this shared component benefits, including team names), rather than a one-off modifier scoped to competitions only — there was no reason for group or team cards to keep the worse truncating behavior. Competition and group both also got `[twoColumnsOnMobile]="true"`, the same opt-in added earlier for disciplines, so all three short-to-medium-length steps are now 2-column from the smallest viewport; only the team step (names can run considerably longer, and carries real crests) stays single-column until the existing 768px breakpoint.

**Grid cards (disciplines above all) now explicitly stretch to the row's full height, instead of relying on CSS Grid's implicit default**: reported live — "Futbol Sala Femení" (a 2-line name) visibly taller than "Futbol Sala" (1 line) on the same row, with the shorter card ending well above its neighbour instead of matching it. By spec, a grid item's `align-items: normal` already resolves to `stretch`, and `.selector-step-list__card` is a plain `<button>` sitting directly as the grid item (no component-host indirection to blame, unlike the match-card fix two entries up) — so this should have stretched on its own, yet the screenshot showed it didn't. Rather than chase the exact browser quirk behind an implicit default silently not applying to a `<button>` grid item, `.selector-step-list--grid` now sets `align-items: stretch` explicitly, and `.selector-step-list__card` gets `height: 100%; box-sizing: border-box;` so its own box actually fills whatever height the stretch gives it — the same "make the default explicit instead of trusting it" fix already applied twice earlier in this file for `.match-list-item`/`.next-match-hero`, just without their extra `:host` flex wrapper, since here the button already is the grid item. Centered content (`align-items: center` inside the card) means the shorter name just sits vertically centered in the taller box now, instead of the box stopping short. That row-level stretch turned out not to be enough — the request was for every card in the grid to match, not just the ones sharing a row, and Grid's row-stretch mechanism has no way to reach across rows (each row is still sized independently by its own tallest item). Fixed by reserving the vertical space for 2 lines of name unconditionally: `.selector-step-list__name` gets `min-height: 2.6em` (its own 15px font-size × 1.3 line-height × 2 lines), so a 1-line name's text box is already as tall as a 2-line name's would be, even before the `-webkit-line-clamp: 2` truncation ever kicks in — every card's content now takes up the same vertical space regardless of row or actual name length, so the card itself renders at a uniform height everywhere, with the earlier row-stretch fix (`align-items: stretch` / `height: 100%`) left in place as a harmless no-op fallback for any future content that isn't text-length-driven.

**Single-line card names weren't vertically centered in that now-uniform box — they sat at the top**: the `min-height: 2.6em` from the previous entry correctly reserved 2-line height, but a plain `display: -webkit-box; -webkit-line-clamp: 2` element has no vertical-centering mechanism of its own — normal block/box text flow starts at the top, and the legacy `-webkit-box-align: center` pairing (the old flexbox spec's `align-items`) was tried first and measured, live, as a no-op in this case. Fixed by splitting the one `&__name` span into two: an outer `&__name` that now does the layout job only (`display: flex; align-items: center; min-height: 39px` — pixels, not `em`, since `em` on this element resolves against its own, non-15px font-size once the `font-size: 15px` moved to the inner element, not the 15px intended), and an inner `&__name-text` span that keeps the actual `-webkit-line-clamp: 2` truncation and typography. The outer flexbox now centers whatever height the inner clamped text actually is (one line or two) inside the fixed 39px slot, instead of the text silently inheriting -webkit-box's default top alignment. Verified by measuring real DOM rects, not just eyeballing a screenshot: a 1-line name now sits with an equal ~9.75px gap above and below it inside its 39px box, and a 2-line name (which already fills the full 39px) is unaffected.

**"Afegeix al calendari" moved to right under the team header, instead of at the bottom of the page**: `TeamCalendarPage` used to render `AddToCalendarButtonComponent` last — after both "Partits jugats" and "Pròxims partits" — so on a real phone, with any real number of matches, the primary action of the whole page sat below a full scroll. Moved to its own `team-calendar__section` right after the crest/name `header`, before either match list. A pure reorder in the template, no new CSS: `.team-calendar` is a flex column with a single uniform `gap: var(--space-xl)` between direct children, so any section slots in cleanly regardless of position, and `AddToCalendarButtonComponent`'s own styling carries no assumption about being last (no `margin-top: auto` or similar). Verified live at phone width with real match data: the button is now the first thing visible after the team name, with zero scrolling needed.

**Upcoming-match cards drop the venue line, and team names center instead of hugging the crest, in the narrow/stacked container-query layout**: reported live from a real screenshot — with the card already stretched to the row's full height (see the stretch-to-row-height entries above) and venue sitting as its own line below the teams row, the whole card read as "too empty, too much white space," especially once two unevenly-tall row siblings forced the shorter one to stretch further. Fixed in two parts. First, `NextMatchHeroComponent`'s `&__venue` block (the pin-icon + venue name, previously the last child, with `margin-top: auto` absorbing leftover stretch height per the earlier entry) is gone entirely — `MatchListItemComponent` already dropped its own venue line in an earlier pass, so this makes both card types consistent again, and removes exactly the content block that was both the least load-bearing (where a match is played matters far less than who's playing and when) and the one creating the dead vertical gap. Second, inside the existing `@container (max-width: 480px)` stacked layout (team rows vertical instead of side-by-side — see the "Team rows stack vertically" entry above), each team row's crest+name group now gets `justify-content: center` on `&__team`/`&__team--away` instead of the implicit left alignment it had before, so a short name no longer leaves a long blank strip beside it on a narrow card. Centering required one more change beyond `justify-content`: `&__name` switches from `flex: 1` (which always grows to fill the row, defeating `justify-content: center` outright) to `flex: 0 1 auto` so it shrinks back to its own content width — but a `display: -webkit-box; -webkit-line-clamp: 2` element combined with `flex: 0 1 auto` and the default `min-width: auto` refused to shrink below its full, unwrapped text width in this browser, which showed up as real match-card text cut off mid-word at the card's right edge, not just a cosmetic quirk caught by eye — so both components' stacked-mode name rule also sets `min-width: 0; max-width: 100%;` to force it back under the flex item's actual available width, the same `min-width: 0` guard the row-layout `&__name` rule already carried for the same reason. Verified live at both a real phone width and the ~470px-wide desktop 2-column grid column (the same sub-480px threshold the stacked layout already treats identically, per the earlier container-query entry).

**Team rows go back to a single row ("Equip 1 vs Equip 2" / "Equip 1 X - X Equip 2"), and finished past-match cards are colored by result instead of carrying a "Finalitzat" badge**: reported live from a screenshot of the stacked layout introduced in the previous entry — seeing each team on its own full-width line, with the score/`vs` sandwiched between them, read worse than the side-by-side row it replaced. Both cards drop the `@container (max-width: 480px)` override (and the now-unused `container-type: inline-size` on the host) entirely, reverting `&__teams`/`&__team`/`&__name` to the single always-horizontal row they had before that entry: crest+name on each side (`flex: 1; min-width: 0`, 2-line clamp), `vs`/score fixed in the middle. This is a deliberate trade-off, not a free fix — the container query existed specifically to stop a long name truncating hard on a narrow card (see "Team rows stack vertically" above), and reverting it brings that risk back: on a real phone a long name can hit the 2-line clamp's ellipsis instead of wrapping fully, visible when testing live at 393px width. Accepted as the explicit request here — a single row matters more than guaranteeing every name's last word is never clipped — but worth knowing if a particularly long name reads badly on a real device later. Separately, `MatchListItemComponent` now colors the whole card by the match's result instead of showing a `app-status-badge` pill for `finished` matches: a new `result` computed signal (`'won' | 'lost' | 'draw' | null`, built on the existing `lost`/`draw` signals the badge coloring already used) drives three modifier classes — `&--won`/`&--lost`/`&--draw` — that swap the card's `background` and add a `border-left: 4px solid`, reusing the exact same status-color tokens the badge itself already used (`--color-status-finished-bg`/`-text` for a win, `-lost-*` for a loss, `-draw-*` for a draw) rather than inventing new colors for the same three meanings. `showStatusBadge` now also excludes `'finished'` (previously only `'scheduled'` was excluded), so the pill disappears exactly when the card color takes over; every other non-scheduled status (`postponed`/`suspended`/`cancelled`/`unknown`) is unaffected and keeps showing its badge on the original plain card background, since those statuses have no result to color by. `NextMatchHeroComponent` never shows finished matches, so it only picked up the row revert, no result-coloring logic.

**Production down again with the same CloudFront `403`, 11+ hours this time — the `Referer`-only fix from the previous incident turned out to not be enough, so more browser-shaped headers were added**: caught live via UptimeRobot (the `/api/health` monitor) and confirmed in the Vercel logs — `/api/health` returning `503` and every `/api/calendar/{groupId}/{teamId}.ics` request returning `502`, both root-caused to the FCF's `disciplines`/`partidos` endpoints returning the identical CloudFront "Request blocked... too much traffic or a configuration error" page as the earlier incident. The first hypothesis — a brand new, broader FCF-side outage unrelated to us — didn't hold up: a real browser clicking through the FCF's own competition page, on a completely different network than Vercel, loaded real match data for the same `grupId` without any problem, which rules out "the FCF's backend is down for everyone" and points back at the same kind of request-shape block as before. But this time the `Referer` header alone — the fix already live in production since the last incident, confirmed present in both `FcfFederationProvider` and `FcfHttpClient` by reading the deployed code — was not enough to avoid the block, meaning the FCF's filter (or AWS WAF/CloudFront Bot Control in front of it) is checking for more than just that one header. Both FCF-calling clients now also send `Origin: https://www.fcf.cat`, `Accept-Language`, and the three `Sec-Fetch-*` headers (`Site: same-origin`, `Mode: cors`, `Dest: empty`) a real same-origin `fetch()` call from the FCF's own page would carry — the same constants (`FCF_ORIGIN`, `FCF_ACCEPT_LANGUAGE`) added once in each file, matching the existing "two separate clients, no shared base class" shape rather than introducing a shared headers module for a four-line addition. This is a plausible next attempt, not a confirmed fix — it hasn't been checked against production yet (needs a real deploy and another look at `/api/health` and the Vercel logs afterward) — and there's a real ceiling worth knowing about before chasing this further: if the FCF's filtering is doing TLS/HTTP2 fingerprinting (e.g. JA3/JA4, a common AWS WAF Bot Control capability) rather than only inspecting headers, no header this app adds from a Node.js `fetch` will ever look identical to Chrome's TLS handshake, and this class of fix is a dead end regardless of which headers are tried.

**The new headers didn't fix it either, and a controlled test from outside Vercel proved this is an IP-level block, not a header or TLS-fingerprint one — so the mitigation shifted from "find the right header" to "degrade gracefully"**: a later Vercel logs check confirmed the `Origin`/`Accept-Language`/`Sec-Fetch-*` headers from the previous entry made no difference — `/api/calendar/{groupId}/{teamId}.ics` kept returning `502` from the same CloudFront "Request blocked" page. Rather than guess at yet another header, or chase the fingerprinting dead-end the previous entry flagged, the next step was a controlled test: run the exact same HTTP request — same headers byte-for-byte — from two different network origins. From a residential network (a plain `curl.exe` from a home connection, headers copied verbatim from what the deployed code sends), the FCF's endpoint answered `200` with real data. From Vercel, the identical request still got `403`. Since the headers were identical in both cases, and `curl`'s TLS stack differs from Node's `undici` just as much as it differs from Chrome's, the one variable left that explains the different outcome is the network the request comes from — this is a block on Vercel's (or AWS's) outbound IP ranges specifically, not anything about the headers or the TLS handshake. That's conclusive enough to close off two of the three previously-considered paths: adding more headers was never going to help (confirmed, not just suspected, by this test), and switching to a headless browser (Playwright) wouldn't help either, since it would still make its request from the same blocked Vercel IP. The two paths that remain are asking the FCF to lift or adjust the block (see the drafted outreach email to `info@fcf.cat`) and, failing that, accepting the block and limiting its damage to users who are already subscribed — which is what the `stale-if-error` change right below this entry does.

**Added `stale-if-error` to every FCF-backed endpoint's `Cache-Control`, so a future outage degrades instead of hard-failing for anyone who already got a successful response**: `calendar-http-handler.ts`, `matches-http-handler.ts`, `team-page-http-handler.ts`, and `catalog-http-handler.ts` all now send `s-maxage=<their existing max-age>, stale-if-error=259200` (3 days) alongside the existing `max-age`. Per Vercel's own Cache-Control docs, `s-maxage` is what actually governs the CDN edge cache — plain `max-age` alone, which is all these endpoints sent before, only ever told the *browser* how long to cache, which is practically meaningless for a `.ics` feed that calendar apps poll server-side rather than through a browser cache, so these endpoints were effectively uncached at Vercel's edge until now. `stale-if-error` tells Vercel's CDN that if the cached entry has expired and revalidating against our function fails — an error response, a timeout, a crash — it should keep serving the last good cached response for up to the stale-if-error window instead of passing the failure through to the client. Dropped `must-revalidate` from the two handlers that had it (`calendar-http-handler.ts`, `matches-http-handler.ts`) when adding this, since its whole point is forbidding exactly the kind of stale-on-error serving `stale-if-error` exists to allow — Vercel's own documented example pairs `s-maxage` with `stale-if-error` and no `must-revalidate`, so keeping both would have meant relying on undocumented, possibly-conflicting behavior rather than a deliberate choice. `health-http-handler.ts` was deliberately left untouched and stays `no-store`: its entire purpose is reporting live FCF health to the uptime monitor, and caching that away would defeat it. Important limitation, stated plainly rather than oversold: this can only help with **future** outages, starting from the first successful response cached under the new header — it does nothing for an outage already in progress when it ships, since Vercel's CDN never had a good response to fall back to during this one. No new infrastructure, no database, no Vercel KV — just a header change, which matches the project's existing "no DB unless truly necessary" stance far better than the alternatives considered earlier.

## What was intentionally left out

- Cache/cron/persistence beyond `Cache-Control` + ETag (see "Design decisions").
- A database.
- Authentication, favorites, user profile, live (in-progress) results — no reliable data source and no clear need for the MVP.
- A full Angular SSR/Universal migration — the bot-only dynamic-rendering rewrite (see "Design decisions") covers the actual need (link previews, non-JS crawlers) at a fraction of the complexity; SSR remains an option later if a real reason shows up (e.g. Core Web Vitals on first paint).
- Sitemap coverage for the other 5 FCF disciplines (Futbol 11/7/5, Futbol Platja) — this app targets futsal; adding them is a one-line change to `SITEMAP_DISCIPLINA_IDS` if the app ever expands.
